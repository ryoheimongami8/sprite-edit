# Sprite Edit — 機能1〜5

スプライトシートを分解してパラパラ動画にし（機能1）、CPU で整数倍に拡大して
開始画像と mp4 を出し（機能2）、編集後の動画をスプライトシートへ戻す（機能3）
ところまでに加えて、esora API（CLI）を呼んで衣装を差し替えた画像・動画を
生成する（機能4・5）ところまで。

## 起動

```
cd D:\40_Esora\04_Splite-edit\app
pip install -r requirements.txt
python app.py --open
```

`http://127.0.0.1:7860` で開きます。ffmpeg は PATH にあるものを使い、無ければ
`imageio-ffmpeg` が同梱している実行ファイルへ落ちるので、別途インストールは
不要です。掴んでいる ffmpeg は画面下部の「環境」に出ます。

**機能4・5 は別途 esora_api_cli のセットアップが必要です。** `esora_api_cli` は
Python 3.12 以上が要るため、このアプリ自身の venv（3.10系でも構わない）とは
別に用意します。

```
py -3.12 -m venv D:\40_Esora\01_CLI\venv
D:\40_Esora\01_CLI\venv\Scripts\Activate.ps1
pip install D:\40_Esora\01_CLI\esora_api_cli-0.4.5-py3-none-any.whl
esora-api auth login
```

このアプリはこの venv の Python を使わず、`esora-api` の実行ファイルを
サブプロセスとして呼ぶだけです。`D:\40_Esora\01_CLI\venv\Scripts\esora-api.exe`
に既定で入っているものとして探しますが、別の場所に入れた場合は環境変数
`ESORA_CLI_PATH` にそのフルパスを指定してください。ログイン
（`esora-api auth login`）はアプリの外で一度済ませておく必要があります —
このアプリ自体はブラウザでの認証フローを持ちません。

## 画面は2つ（上部のスイッチで切り替え）

**かんたん（既定）** — 1 画面。アップロードするのは3つだけで、あいだの
受け渡しはアプリがやります。

```
① スプライトシート ─┬─▶ 機能1 ─▶ 機能2 ─▶ First Frame / スプライト動画
② 変更案の画像 ─────┘         └─▶ 機能4 ─▶ 変更後 First Frame
                                        ↓
                            【手作業】esora 等で動画生成（旧・機能5）
                                        ↓
④ 変更後の動画 ────────────▶ 機能3 ─▶ ⑤ 最終スプライトシート
```

機能5（アプリ内での動画生成）は精度が出ないため、かんたん画面では扱いま
せん。ステップ1 が出す「スプライト動画」と「変更後 First Frame」をその
ままダウンロードできるようにしてあるので、それを手作業の生成に渡し、
できた動画をステップ3 に入れます。

**機能4 が失敗しても機能1・2 の結果は残ります。** esora 側の理由（未サイン
イン、モデルid違い、生成失敗）で落ちるのは日常的に起きますが、そのたびに
120 フレームの拡大をやり直す必要はありません。結果欄に `[機能4は失敗]` と
理由が出て、First Frame とスプライト動画はそのまま使えます。

ステップ3 の「対象セッション」は既定で最新のセッションを指します。手作業の
動画生成には時間がかかり、ステップ1 とステップ3 が別の日になることも
あるので、アプリを再起動しても続きから実行できます。

**詳細（旧UI）** — 機能ごとのタブ。工程を1つずつ確かめたいとき用で、
機能5 のタブもこちらに残してあります。どちらの画面も同じセッションを
見ているので、かんたん側で作った作業をそのまま旧UI で続けられます。

## 設計上の約束

**新しい中間ポーズは 1 枚も作りません。** 尺は同じ絵の複製だけで作ります。
24fps にすることと動きを滑らかにすることは別で、ここでやっているのは前者
だけです。

**各コマを中央寄せしません。** コマは共通のセルにそのまま置きます。個別に
中央寄せすると元の上下動やコマ間の位置関係が失われ、生成後に「元のポーズと
同じ位置か」を比べる基準そのものが消えます。

**拡大は整数倍の最近傍のみです。** 1024 ちょうどに合わせようとすると 114px
のセルでは 8.98 倍になり、元の 1 画素が場所によって 8px になったり 9px に
なったりします。倍率のほうを整数に固定し、目標寸法を譲ります（114px → 9 倍
= 1026px）。倍率は素材ごとに、セルの長辺が目標にいちばん近くなる整数を
自動で選びます。

**透過は切り出した直後に別途保存します。** 合成後の画からアルファを推定し
直す設計にはしていません。半透明の縁は背景と混ざったあと元には戻らないので、
最終的な透過精度を背景除去に任せない、というのがこの分け方の理由です。

**機能2 の入力は mp4 ではなく連番 PNG です。** 一度 H.264 を通した画を拡大
すると、圧縮でにじんだ色をそのまま 9 倍に引き伸ばすことになります。mp4 は
目視確認用の副産物です。

**機能3 は動画から 1 枚選ぶだけで、新しい中間フレームは作りません。** 各
ポーズの保持区間の中央（既定）にあたる 1 枚を選び、元のセル寸法へ縮小して
貼り戻すだけです。位置合わせ（ずれの補正）はまだ入れていません。

**機能3 のフレーム対応は index ではなく時間比率で決めます。** 編集後の
動画は元と同じフレーム数・fps で返ってくるとは限りません（検証動画は
120→121 フレーム）。だから「元タイムラインの何 % の位置か」を先に出し、
実際の動画のフレーム数へ掛け直します。動画の尺が元の想定と 15% 以上ずれた
ときは結果に `[注意]` を出しますが、それでも比率で選ぶので動作はします。

**機能3 はセルへマスクを渡さずにコピーします。** 透明なキャンバスへ
`paste(tile, pos, tile)` と書くと、tile 自身のアルファがマスクとしても
使われ、アルファが二乗されます（出力 = round(元^2/255)）。以前の実装が
これで、実測で全 77,748 画素がこの式に一致しました。アルファ 64 の影が
16 まで薄まり、同時に RGB へ背景色が残るため影が薄紫になります。重ならない
セルへの書き込みにマスクは不要です。**実行のたびに、元アルファ版のアルファ
が元スプライトと一致するか機械で照合して結果に出します**（目視では薄さの
違いに気づけないため）。

**機能3 は背景の処理を縮小の前に、高解像度のまま行います。** 縮小してから
背景を抜くと、縮小の補間で背景色が輪郭に練り込まれたあとの画を相手に
することになり、そこはもう分離できません。順序は
「代表フレーム取得 → 高解像度で背景判定 → 高解像度で色被り補正 →
アルファを考慮した縮小（プリマルチプライド）→ アルファ付与 → 影の復元 →
マスク無しでコピー」です。

**「透明にする範囲」と「残す画素の色を直す量」は別の設定です。** tolerance
だけを強めると背景と一緒に剣・蹄・袖の輪郭も消えます。`keying.py` は
`background_alpha()`（形の問題）と `unmix_background()`（色の問題）に
分かれています。

**機能3 の透過は 2 方式を同時に出します。** どちらが良いかは素材と生成
モデル次第で決め打ちできないため、`sprite_original_alpha.png`（元コマの
アルファをそのまま適用）と `sprite_chromakey.png`（機能1 で塗った背景色を
キー抜き）の両方を書き出し、見比べて選んでもらう設計にしています。

## 格子の自動検出について

アルファの空白列からコマ境界を取り、間隔の基本ピッチを割り出して、全コマに
同じセルを当てます。空のコマを挟んでいても、間隔が基本ピッチの整数倍で現れる
ことを使って復元します。

効かないのは次の場合です。

- **背景が透過ではなく単色で塗られたシート** — 境界が見えません
- **コマの中に完全な透明列があるシート** — 1 コマが 2 つに読まれます

どちらも「格子の合計寸法がシートと合わない」形で表に出るので、その場合は
結果欄に `[注意]` が出ます。セル寸法を 0 のままにして **列数・行数だけ** 
入れ直せば、シート寸法から割り算でセルを出します。

## 機能3 の色被り補正について

機能1 は透過画像を背景色 B の上に合成しました。つまり観測色は
`C_obs = C_true*a + B*(1-a)` という既知の式で作られています。これを解き
直せば元の色が戻ります（`C_true = (C_obs - B*(1-a)) / a`）。a が 1 に近い
内側では何も起きず、a が小さい輪郭だけが直ります。

使うアルファは版ごとに違います。**元アルファ版では、正しい被覆率をこちらは
既に知っている**ので、色距離で推定し直さず元のアルファを動画の解像度へ
引き伸ばして使います。影や輪郭のような「背景と被写体の中間色」は色距離では
判定できません — 背景からも被写体からも遠いため不透明と誤って扱われ、色被りが
残ります。実測ではこの変更でマゼンタ残留が 1,387px → 385px に減りました。

逆合成の結果が 0-255 をはみ出す画素では、その前提が成り立っていません
（使ったアルファが実際の被覆率と合っていない）。そこでは**はみ出さずに済む
最大の補正量まで自動で緩めます**。閾値で線を引く代わりに画素ごとにデータが
支持する量だけ効かせる形で、マゼンタ背景では行き過ぎがそのまま緑への転びに
なるため、この頭打ちが効きます（緑の斑点 472px → 140px、マゼンタ残留は
393px を維持）。

## 機能3 の影の扱いについて

影の領域には「背景色と混ざった生成側の RGB」が入ります。**アルファだけを
戻しても、RGB に混ざった背景色は取り除けません** — 半透明の黒い影が紫色の
影になります。影は元スプライトの RGB ごと戻します。

問題は影の見分け方です。「半透明の画素はすべて影」は使えません。剣にも兜にも
馬の輪郭にもアンチエイリアスの半透明画素があり、検証素材では候補 2,769px の
うち 1,089px が輪郭線でした。分けているのは **形** です — 影は面、輪郭は線。
3x3 の収縮で 1px 幅の線は消え、面は芯が残ります。その芯を膨張で戻して元の
候補集合で頭打ちにします（モルフォロジーの開処理）。実測で判定領域が
y=9-80 から y=67-80 の接地帯だけに絞られました。

影マスクは機能1 が作って `01b_shadow_masks/` に保存します。合成後の画からは
作れません — 背景と混ざったあとでは、半透明の黒が影だったのか背景だったのか
区別できないためです。

## 機能3 のクロマキーについて

`sprite_chromakey.png` は機能1 で選んだ背景色に近い画素を透明にします。
二値の閾値ではなく、`tolerance` から `tolerance + 縁のやわらかさ` の間で
線形に不透明度を落とすソフトエッジ方式です。生成 AI が背景を完全には
保てないことが多く、その場合は縁に元の背景色の色被りが残ります。それは
閾値を甘くしても直らない種類のずれなので、そのときは `sprite_original_alpha.png`
（元コマのアルファを使う版）と見比べて選んでください。

## 機能4・5 について（esora API 呼び出し）

機能1〜3 と違い、ここでの「処理」はローカルの画素操作ではなく esora の
サーバーへの生成依頼です。`backend/esora_cli.py` が `esora-api --json ...`
をサブプロセスとして呼び、JSON（進行中は JSON Lines、完了時は1個の
JSONオブジェクト）を読むだけの薄い層になっています。ログイン
（`esora-api auth login`）はこのアプリの外で事前に済ませておく前提で、
未サインインならそのままエラーとして「結果」欄に出ます。

**モデルの id はハードコードしていません。** 「GPT image2」「Seedance 2.0
Fast」はユーザーから見た表示名で、esora 側の実際の model id と一致する
保証がありません。各タブの「② モデルを確認」ボタンが `model list --task
image|video --json` をそのつど呼び、id と label の両方にキーワードを含む
ものを候補として出します（無ければ全件を出すので、そこから手で選べます）。

**esora には `@img:1 ▾` のような番号付き参照記法はありません。** これは
esora の Web版が入力補助として見せているチップの表示で、CLI 経由で送る
プロンプト文字列にその記法自体が乗ることはありません（`esora_api_cli` の
ソースを直接確認しましたが、`@img` を解釈する処理はどこにもありません）。
CLI 自身のヘルプにも「モデルには番号は伝わらないので、位置で語るなら
"1枚目の参照画像" と書け」とあるため、機能4 のプリセットプロンプトは
`config.DEFAULT_IMAGE_PROMPT` でその言い方に置き換えてあります。
`--img-ref` は「1枚目=画像1（ベース） → 2枚目=画像2（デザイン参照）」の
順で渡すので、UI で順序を変えたらプロンプトの言い回しも合わせてください。

**機能5 に動画をそのまま参照として渡す経路は無い。実機で確認済み。**
esora の CLI に動画参照の専用オプション（`--vid-ref`）は無く、未実装として
ドキュメントに残っているだけである。以前はクライアント側の型チェックを
迂回して動画由来の asset_id を `--img-ref` に渡せないか試したが、

```
"Asset ... is video; reference images must be images"
```

とサーバー側が明示的に拒否することを実際の生成リクエストで確認した
（`invalid_request`）。つまり esora は現状、動画そのものからの動作・
タイミングの取り込みに対応していない。

代わりに `backend/feature5.py` が参考動画から等間隔で
`config.VIDEO_REFERENCE_FRAME_COUNT`（既定6）枚の代表フレームを ffmpeg
（`video.decode_sequence`）で抜き出し、**通常の画像参照**として渡す。
`--img-ref` は「代表フレーム(この枚数) → 衣装参照画像(最後の1枚)」の順に
並ぶので、`config.DEFAULT_VIDEO_PROMPT` も「1枚目からN枚目＝ポーズの基準
／最後の1枚＝衣装の基準」という言い方に書き換えてある。動画の正確な
タイミング（何秒でポーズが切り替わるか）そのものは渡せないため、静止画の
枚数と順序でポーズの流れを伝え、保持時間や切り替え方（補間しない・瞬時に
切り替える、など）はプロンプトの文章に委ねている。これは esora が普通に
サポートしている画像参照の使い方なので、以前のような「サーバーが拒否
するかもしれない」という不確実性は無い。

## まだ入れていないこと

- 全コマ共通のバウンディングボックスで一括トリミングする選択肢。今は
  114x114 のセルをそのまま拡大するので、騎手が 1026px の画面のうち 270px
  程度にしかなりません。相対位置を保ったまま余白を詰めれば、被写体に
  割ける画素は倍近くになります
- 機能3 の位置合わせ（生成後の絵が元コマからずれたときの補正）。
  今は動画から選んだ 1 枚をそのまま縮小して貼るだけです。元の輪郭内に
  生成側の背景が入り込むほどポーズがずれている場合、色補正だけでは
